# Проверка исходящего TCP: FturnRaw 0.1.12

В редакторе профиля появился пункт **Исходящий TCP**:

- **По пакетам — прежний режим** (`packet`): общая очередь для всех TURN-каналов. Это значение по умолчанию для существующих профилей.
- **По соединениям — экспериментальный** (`tcp-flow`): исходящие пакеты одного TCP-соединения закреплены за одним готовым TURN-каналом. Новые соединения распределяются между готовыми каналами по кругу. Подключение дополнительного канала не переносит уже активное соединение.

Изменение действует после переподключения. Обновлять сервер и менять ключ, MTU или порт для этой проверки не требуется. CLI: `-raw-uplink packet` / `-raw-uplink tcp-flow`.

## Что проверяет эксперимент

Распределение соседних пакетов одного TCP-соединения между каналами с разной задержкой может нарушать порядок доставки. Режим по соединениям устраняет этот источник перестановок на исходящей стороне. Он не восстанавливает порядок пакетов в сети и не добавляет повторную передачу на уровне Raw.

Скорость одного TCP-соединения теперь ограничена выбранным каналом. Несколько TCP-соединений могут использовать разные каналы. UDP, ICMP, фрагменты IPv4 и серверное распределение входящего трафика сохраняют прежнюю схему. Это отдельный эксперимент для TCP-выгрузки; улучшение пинга игровых UDP-пакетов им не обещается.

При отказе канала его очередь сбрасывается; TCP сам повторяет потерянные пакеты, а следующие пакеты закрепляются за другим готовым каналом. Пакеты, уже отправленные до отказа, ещё могут прийти позже. Привязки без активности более двух минут назначаются заново; таблица ограничена 8192 соединениями, при заполнении удаляется самая старая привязка.

## Очереди и логи

Общий лимит остаётся 256 ожидающих пакетов, включая центральную очередь, общую очередь и очереди каналов. У отдельного TCP-канала предел 64 пакета. Переполнение вызывает сброс, а не перенос текущего соединения на другой канал.

Раз в 10 секунд строка `[RAW UPLINK]` показывает:

- `mode`: выбранный режим;
- `queued`: текущее число ожидающих пакетов;
- `enqueue_drop`: сбросы при общем переполнении, с начала подключения;
- `path_drop`: сбросы при переполнении очереди канала или её удалении, с начала подключения;
- `failovers`: переназначения активной привязки после исчезновения канала;
- `queue_wait_max_ms`: максимальное ожидание отправленного пакета в очереди за последний интервал. Время записи в сокет сюда не входит.

## Сравнение

1. Оставить один сервер, MTU, транспорт TURN, профиль RTP, число каналов и один сервис замера. Дождаться готовности одинакового числа каналов.
2. Измерить TCP-выгрузку в режиме по пакетам: один TCP-поток и четыре параллельных.
3. Переподключить тот же профиль в режиме по соединениям и повторить тест.
4. Вернуться к режиму по пакетам и повторить ещё раз. Сохранить скорости и строки `[RAW UPLINK]` для всех трёх запусков.

Нельзя считать причину полностью доказанной до такого сравнения на действующем маршруте. Результат одного Speedtest, особенно с другим сервером измерения, недостаточен.

Ссылки конфигурации с экспериментальным режимом используют формат v4. Старые ссылки v1–v3 читаются с режимом по пакетам; ссылки без нового режима продолжают экспортироваться в прежних форматах. Для импорта v4 нужен клиент с поддержкой этой версии.

## Локальная проверка

Проверены неизменность привязки при добавлении канала, FIFO одного соединения, перенос после отказа/пересоздания канала, ограничение общего бюджета и таблицы привязок, переполнение очереди, распознавание TCP/фрагментов, отмена ожидания готового канала, сохранение/экспорт/импорт профилей. Интеграционные тесты передают 32 TCP-пакета по 1500 байт через настоящий локальный Pion TURN для обоих транспортов и обоих профилей RTP, а также проверяют обычный UDP и обратное направление.

Рабочий туннель и серверные процессы в этих тестах не используются.
