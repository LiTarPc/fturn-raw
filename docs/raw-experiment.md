# Экспериментальный Raw IP для fturn

Отдельный проект `fturn-raw-experimental`, ветка `experiment/raw-ip`.
Исходная версия сохранена в первом коммите. Новые программы: `raw-client` и
`raw-server`; прежние `client` и `server` продолжают работать.

## Что реализовано

```text
IPv4 из TUN → RTP + ChaCha20-Poly1305 → TURN → UDP → TUN на VPS
```

WireGuard/AmneziaWG, DTLS, KCP и smux в этом пути отсутствуют. Внешние TURN,
TCP/UDP, RTP и шифрование остаются. TCP/UDP внутри исходного IP-пакета передаются
без изменения. Клиент использует существующий VK-провайдер fturn: ссылки,
креды, CAPTCHA, несколько потоков и получение новых аллокаций после обрыва.

Первый прототип рассчитан на **один клиентский IPv4-адрес на один процесс
сервера/ключ**, до 64 TURN-потоков. По умолчанию 10.77.0.1/24 на сервере,
10.77.0.2/24 на клиенте; MTU CLI по умолчанию 1280. На проверенной установке выбран 1420. Адрес и MTU задаются заранее на обеих сторонах.
Два клиента с одним ключом/адресом использовать одновременно нельзя: новое
подключение заменяет потоки предыдущего процесса.

Это собственный экспериментальный протокол, вдохновлённый подходом Raw в qWDTT.
Он **не совместим по сети с qWDTT и обычным сервером fturn**. Исходники qWDTT
в этот проект не переносились. GUI, Android/iOS TUN-fd, IPv6, динамическая выдача
адресов, несколько пользователей и автоматическая настройка полного VPN здесь
пока не реализованы.

Реальная установка и управление: [raw-deployment.md](raw-deployment.md).
Результаты проверки: [raw-validation.md](raw-validation.md).

## Готовые сборки и повторная сборка

- Windows x64: `dist/windows-amd64/raw-client.exe` и `raw-server.exe`.
- Linux x64: `dist/linux-amd64/raw-client` и `raw-server`.
- Linux ARM64: `dist/linux-arm64/raw-client` и `raw-server`.
- ZIP-пакеты: `dist/fturn-raw-<платформа>.zip`.

Сборка из корня проекта, Go 1.26.6 или новее:

```powershell
.\scripts\build-raw.ps1
```

Скрипт кладёт рядом с Windows-программами официальный `wintun.dll` 0.14.1,
проверяя SHA256 ZIP по опубликованному хешу. Драйвер при сборке не устанавливается.
Для изменения интерфейса при запуске нужен PowerShell от администратора.
Linux требует `/dev/net/tun`, `iproute2` и root/CAP_NET_ADMIN.

## 1. Подготовить отдельный ключ

На VPS:

```bash
chmod +x raw-server
umask 077
./raw-server -gen-obf-key > raw.key
```

Передайте этот же файл `raw.key` на клиент по своему защищённому каналу.
Ключ должен быть отдельным от ключей обычного fturn. Не публикуйте его.
Непрозрачный профиль `none` запрещён: Raw всегда шифруется.
Поддерживаются `rtpopus` и `rtpopus2`, профиль должен совпадать на обеих сторонах.

## 2. Запустить Raw на VPS

Откройте входящий **UDP 56010** в firewall VPS. Клиент может подключаться к
TURN по TCP, но от TURN до VPS пакеты всё равно идут по UDP.

```bash
sudo ./raw-server \
  -listen 0.0.0.0:56010 \
  -tun ftraw0 \
  -address 10.77.0.1/24 \
  -client-ip 10.77.0.2 \
  -mtu 1420 \
  -obf-profile rtpopus2 \
  -obf-key-file raw.key
```

Если сеть 10.77.0.0/24 уже используется, выберите свободную и измените параметры
на обеих сторонах. Этот процесс создаёт только свой TUN и адрес. NAT и правила
пересылки на VPS он автоматически не меняет.

## 3. Запустить клиент Windows

Распакуйте Windows ZIP, положите `raw.key` рядом с программой. В PowerShell
**от администратора**, из каталога сборки:

```powershell
.\raw-client.exe `
  -peer "VPS_IP:56010" `
  -links "https://vk.ru/call/join/ВАШ_ХЕШ" `
  -n 3 `
  -transport tcp `
  -tun ftraw0 `
  -raw-address 10.77.0.2/24 `
  -raw-mtu 1420 `
  -obf-profile rtpopus2 `
  -obf-key-file .\raw.key
```

Для Linux те же параметры; запустите `sudo ./raw-client`. При необходимости
используйте обычные флаги VK/DNS, например `-manual-captcha`, `-dns-mode doh`.
Флаги `-tunnel`, `-obf-timing` и TCP-прокси `-mode tcp` в Raw не поддерживаются.
Если `-links` содержит несколько ссылок, число потоков равно `-n × число ссылок`.

Дождитесь сообщений `RAW stream ... ready`. Проверьте:

```powershell
ping 10.77.0.1
```

Программа **не меняет маршрут по умолчанию**. На первом этапе достаточно
доступа к 10.77.0.1: он позволяет проверить TUN и измерить скорость до VPS,
не переключая весь интернет компьютера.

## 4. Доступ в интернет для выбранного тестового адреса

Для проверки выхода через VPS сначала настройте forwarding и NAT. Пример
для VPS с iptables; замените `eth0` своим внешним интерфейсом:

```bash
sudo sysctl -w net.ipv4.ip_forward=1
sudo iptables -A FORWARD -i ftraw0 -o eth0 -s 10.77.0.2/32 -j ACCEPT
sudo iptables -A FORWARD -i eth0 -o ftraw0 -d 10.77.0.2/32 -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
sudo iptables -t nat -A POSTROUTING -s 10.77.0.2/32 -o eth0 -j MASQUERADE
```

На Windows направьте один тестовый IP через Raw:

```powershell
New-NetRoute -DestinationPrefix "1.1.1.1/32" -InterfaceAlias "ftraw0" -NextHop "0.0.0.0" -PolicyStore ActiveStore
ping 1.1.1.1
```

На Linux:

```bash
sudo ip route add 1.1.1.1/32 dev ftraw0
ping 1.1.1.1
```

Для удаления тестового маршрута Windows:

```powershell
Remove-NetRoute -DestinationPrefix "1.1.1.1/32" -InterfaceAlias "ftraw0" -Confirm:$false
```

На Linux: `sudo ip route del 1.1.1.1/32 dev ftraw0`.
Для удаления NAT/forwarding используйте те же команды iptables с `-D` вместо
`-A`. Значение IP forwarding верните к значению, которое было до эксперимента,
если его меняли только для этого теста. Существующие правила не очищайте.

Полный VPN с маршрутами 0.0.0.0/1 и 128.0.0.0/1 требует отдельной настройки
исключений для TURN и VK API, DNS и IPv6. Не добавляйте эти маршруты вслепую:
получение новых TURN-кредов после обрыва может оказаться внутри неработающего
туннеля. `-routes` умеет сохранять отдельные IPv4-маршруты к TURN, но не решает
весь этот сценарий. Проверка полного VPN — следующий этап после измерений.

## 5. Сравнение скорости

Если установлен iperf3, на VPS:

```bash
iperf3 -s -B 10.77.0.1
```

Разрешите TCP 5201 со стороны TUN в firewall VPS. На клиенте:

```bash
iperf3 -c 10.77.0.1 -t 30
iperf3 -c 10.77.0.1 -t 30 -R
iperf3 -c 10.77.0.1 -t 30 -P 4
```

Сравните с WG+fturn, подключаясь к соответствующему внутреннему адресу WG.
Используйте один VPS, одни VK-ссылки, одинаковое число потоков, одинаковый
внешний транспорт и тесты в близкое время. Сделайте по 3–5 измерений в каждую
сторону; фиксируйте медиану, загрузку CPU, ретрансляции TCP и задержку.
Числа из qWDTT нельзя считать результатом этого прототипа. На реальной сети
VK/VPS скорость пока не измерена.

## Протокол и защита

- RTP/Opus с ChaCha20-Poly1305; профиль `rtpopus2` добавляет RTP extension.
- Ключи направлений и Raw-протокола отделены HMAC-SHA256 от основного ключа.
- Каждая аллокация получает случайный challenge сервера; новые ключи сессии
  выводятся из обоих случайных токенов и идентификатора процесса клиента.
- IP-пакеты передаются только после зашифрованного подтверждения challenge.
- Внутри шифрованного data-пакета добавляется один байт типа сообщения.
- После проверки AEAD применяется окно защиты от повторов на 2048 счётчиков.
- Сервер проверяет исходный IPv4 клиента, клиент — IPv4 назначения.
- Keepalive: 10 секунд; неактивный поток клиента пересоздаётся, а сервер
  удаляет старые/незавершённые потоки. Новый процесс клиента заменяет старые.

Это экспериментальный собственный протокол, без независимого аудита.
Удаление DTLS не означает удаление аутентификации: здесь остаётся общий ключ
и подтверждение новых ключей сессии. Утечка общего ключа даёт доступ как этот
единственный клиент. Отдельный прототип не является готовой заменой
многопользовательского VPN или Android-приложения.

## Проверки

```bash
go test ./...
go vet ./...
go test -v ./internal/rawvpn
go test -run '^$' -bench BenchmarkEncryptedRawRoundTrip -benchmem ./internal/rawvpn
```

Новые проверки запускают настоящий Pion TURN на loopback по UDP и TCP,
передают IPv4-пакеты через три параллельных потока в обе стороны, проверяют MTU,
подмену исходного IP, повторы, неверные ключи, отражение пакетов, разделение
сессий, потерю ответов handshake, замену старого процесса и остановку клиента.
TUN заменён устройством в памяти: создание настоящего Linux TUN, Wintun,
маршрутизация, NAT и доступ через VK требуют проверки на ваших устройствах.

## MTU и fingerprint

Поддерживаются значения 576..1500. После смены MTU перезапустите обе стороны
с одинаковым значением. Пакеты IPv4 больше 1350 байт разбиваются внутри Raw
на два отдельно аутентифицированных сообщения; наружные датаграммы не выросли.
Полный IP-пакет собирается до передачи в TUN. Незавершённые сборки ограничены
64 пакетами на сессию и сроком 3 секунды; перестановка частей допускается.
Эта версия нужна на обеих сторонах для MTU выше 1350.

На проверенном VPS внешняя сеть сообщила path MTU 1472. MTU 1500 прошёл до
TUN сервера, но большой интернет ICMP-пакет 1500 не получил ответа. Поэтому
установлен MTU 1420: пакеты этого размера прошли до сервера и 1.1.1.1.

Запрос к BrowserLeaks через реальный Windows Raw TUN, сделанный curl без прокси,
показал MTU 1420, MSS 1380 и Link Type generic tunnel or VPN. Zardaxt дал
Android 37%, Linux 32%, Windows 28%, macOS 6%, iOS 5%. Это оценки одного запроса;
они не доказывают, что Windows стал Android. Размер MTU меняет MSS, но ОС
определяется также по TCP options, окну и TTL. Link Type и оценка ОС — разные
поля. Результат другого браузерного запроса может отличаться.

Личный Test-BrowserLeaks.ps1 в dist/deployment-windows проверяет ping с DF и
временно направляет IP BrowserLeaks через Raw; после запроса убирает маршрут.
Обычный браузерный трафик продолжает идти по ранее настроенному маршруту.
